### Unit of count

One count is one **(app, advisory group)** pair, where an advisory group is one row group from
`scan_inventory.py`: aliases merged, malicious-package entries excluded. The same advisory reached
in two apps counts twice. The same advisory reached by two paths in one app counts once.

### What gets traced

These are the matched non-malicious advisory groups where the vulnerable package is a **library**
the app imports. Each group gets exactly one bucket.

- **X, no symbol.** The advisory neither names a function nor links a fix commit. If it links one,
  no single vulnerable function can be identified from it. Not traced, not counted.
- **S, not called by app code.** The package is a server, CLI or build tool (gunicorn, uvicorn,
  pip and similar). It calls the app; the app does not call it. Not counted.
- Otherwise, take the **true vulnerable symbol** from the fix commit: the function or method whose
  body the fix changes to remove the flaw. Ignore tests, docs and changelog edits in that commit,
  and ignore refactors that are not the fix. If the fix touches several functions, any one counts
  as the target. Trace from app code. Then the pair gets exactly one of:
  - **E, explicit-call path (counted toward the threshold).** A chain of call expressions from a
    function in app code to the true symbol. Every edge is a syntactic call `f(...)` or
    `x.f(...)`. The callee is identified by reading imports, names and the receiver's construction
    in the source, whether that code sits in the app or in the library. Each edge is written as
    `file:line caller -> callee`. An edge that needs the receiver's type worked out by hand is
    marked `(receiver typed by hand: <why>)` so it can be checked.
  - **A7, property read or framework callback only (counted separately).** Every path found needs
    at least one non-call edge: an attribute or property read (e.g. `request.POST` triggering a
    parser), a framework invoking an app-registered class or handler (settings lists, decorators,
    signal receivers, middleware), or a dunder or implicit protocol call.
  - **N, no path found.** Reasonable search found no call site that leads to the symbol.
  - **U, unsure.** Anything I am not sure of. Never counted as E or A7.

"App code" means the app's own Python files under the traced directory. It excludes test files
(`tests/`, `test_*.py`, `*_test.py`, `conftest.py`), migrations, `.venv/` and vendored
third-party code. A path that starts only in tests does not count. Reachability of the symbol is
what is counted, not exploitability: a call that reaches the vulnerable function counts even when
the dangerous input or configuration is absent.

Search tool: `grep -rn --exclude-dir=.venv --include="*.py"` over app code, plus reading the
library source at the pinned version.

### Thresholds (on the E count summed over traced apps)

- **≥ 5** → proceed with plan A′.
- **1-4** → proceed with the plan, with a dataset-led headline.
- **0** → pivot to plan C′ (`reports/v1 final push plan.md`, "C′. If the spike fails").

The two sources disagree on the 1-4 band. The council kill criterion pivots to C whenever there

### Caveats on the E count (read before citing it)

These do not change the count or the rule. They describe what the 16 are.

1. **All 16 pairs come from one app (open-webui).** The other 7 apps gave 0. Eleven come from one
   package version, pyjwt 2.13.0, which has 15 open advisories in this snapshot.
2. **The 16 pairs share 11 distinct true symbols.** For example, GHSA-r6x4, GHSA-p4g4 and
   GHSA-w2cx all reach `HMACAlgorithm.prepare_key`.
3. **11 of the 16 paths contain an edge whose receiver I typed by hand.** These are all 10 pyjwt
   pairs that go through `jwt.decode` (a module-level alias of a bound method, plus `self._jws`
   and the `_algorithms` dict lookup) and the sentence-transformers pair (`super().__init__`).
   The L3 rules in `CLAUDE.md` treat `super()` as unresolved. There are **5 pairs with no
   hand-typed edge** (only imports, constructors and `self.method()`): GHSA-5849, GHSA-4vqv,
   GHSA-x3rh (pypdf), GHSA-w6j9 (pyjwt `PyJWKSet.from_dict`) and GHSA-3w57 (anyio).
4. **GHSA-9j54 reaches the changed function but not the changed branch.** The fix (`f91ed44`)
   edits only the `isinstance(key, PyJWK)` branch of `_verify_signature`. open-webui passes a
   `str` (`auth.py:241`) or `signing_key.key` (`oauth.py:2438`), so that branch is not taken. It
   counts under the pre-registered rule, which counts the function, not the branch.
5. A path counts from a function in app code. I did not prove that each app entry function (for
   example `decode_token` or `PDFLoader.lazy_load`) is itself reachable from a route.
   `decode_token` has 5 callers in app code (`utils/auth.py:335`, `utils/auth.py:443`,
   `main.py:2348`, ...).
6. U is large (91) because most matched packages are **transitive**: the app never imports them.
   I did not trace through intermediary libraries (e.g. requests → urllib3, ldap3 → pyasn1,
   huggingface_hub → filelock). Every such pair is U, never N.
