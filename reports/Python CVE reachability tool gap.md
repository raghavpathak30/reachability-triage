# Python reachability needs proof, not features

As of November 2026, function-level CVE reachability for Python is a solved product category for anyone who pays: Endor Labs, Snyk, Socket/Coana (Enterprise), Checkmarx, Mend and Semgrep all ship some form of it. Among free, open-source and actually adopted tools, though, the slot is empty. pip-audit and `uv audit` match versions only. OSV-Scanner's Python call analysis is an import-level prototype that has stalled. GitHub withdrew its 2022 Python "vulnerable calls" beta and relaunched reachability for JavaScript/TypeScript only. OWASP dep-scan's documented verdict is per package. That gap is real but small and closing, and roughly ten tiny 2026 repositories already claim the same feature list: call path, three-state verdict, OpenVEX/SARIF, offline mode. A new tool cannot own "first" or "features". The parts nobody owns are the data and the proof. Only **2 of 14,236** live non-malware PyPI advisories carry machine-readable symbol data. **0 of 6,873** GitHub-reviewed pip advisories list vulnerable functions. No public, function-level Python reachability benchmark exists. reachability-triage's app scan deliberately never says `not_reachable`, so it cannot sell "what you don't need to patch". It can honestly own three things: proven call paths with nothing marked safe, an open dataset mapping advisories to symbols with provenance, and a published evaluation of both. That is a narrow niche, credible only if the data and the evaluation ship. One more constraint shapes the wording below: in the repository today, the app scan does inventory and OSV matching only. Wheel diffs, target symbols, call graphs and evidence levels are specified but not built ([DECISIONS.md §27, item 12](../DECISIONS.md)), so the headline claim is a target, not a present-tense fact.

## Paid tools own Python function-level reachability; free ones stop at the package

The reference point is Go. govulncheck is trusted because the Go Security team curates package and symbol data for every reviewed report. It "only surfaces vulnerabilities that actually affect you, based on which functions in your code are transitively calling vulnerable functions," with a call stack as evidence ([go.dev](https://go.dev/doc/security/vuln/)). Practitioners now ask for the same thing in Python by name. Filippo Valsorda's February 2026 essay "Turn Dependabot off" called Dependabot "a noise machine" ([words.filippo.io](https://words.filippo.io/dependabot/)). Its Hacker News thread (647 points) turned at once to "why is there no govulncheck for Python?" There, pip-audit's maintainer argued that "most non-obfuscated Python is essentially static" and that the bigger problem is "_encoding_ vulnerable API information" ([HN 47094192](https://news.ycombinator.com/item?id=47094192)).

The free and open-source tools leave that request unmet. **OSV-Scanner v2.7.1** (11,540 stars) runs call analysis for Go by default and for Rust experimentally. It has no Python call analysis. Its Python call-graph issue has been open since September 2025 with only a stale-bot reply ([osv-scanner#2225](https://github.com/google/osv-scanner/issues/2225)). The one merged Python work is "coarse" import-level reachability for `poetry.lock` ([osv-scanner#2540](https://github.com/google/osv-scanner/issues/2540)). **pip-audit** has no reachability and no issue requesting it ([pip-audit](https://github.com/pypa/pip-audit)). **GitHub** launched Python vulnerable-function alerts in 2022 with data for "79 Python advisories" ([community discussion 15010](https://www.Github.com/orgs/community/discussions/15010)). A 2026 docs PR now states that the `has:vulnerable-calls` filter "is no longer supported" ([github/docs#45849](https://github.com/github/docs/pull/45849)). GitHub's October 2026 reachability preview covers JavaScript and TypeScript only ([GitHub changelog](https://github.blog/changelog/2026-10-28-prioritize-dependabot-alerts-with-reachability-analysis/)). **OWASP dep-scan** (1,405 stars) is the one established OSS project that claims Python reachability. Its README describes a vulnerable *package* being "on an executed path" ([dep-scan](https://github.com/owasp-dep-scan/dep-scan#readme)), and nobody has verified whether it matches advisory-specific functions. That is the most important unverified fact in this landscape. **Astral's `uv audit`** shipped in preview on 2026-06-08. Its roadmap lists improved "finding precision" through `uv`/`ty` static analysis and reachability ([Astral blog](https://astral.sh/blog/uv-audit)), and that is the most credible threat to the gap.

The commercial side shows two things that matter for positioning. First, **vendor "unreachable" shares of 80 to 98% are measured with each vendor's own tool as the oracle.** Semgrep's 31 of 1,614 Dependabot alerts is one example ([Semgrep](https://semgrep.dev/blog/2024/overrated-and-underperforming-transitive-reachability-analysis)). Endor's "fewer than 9.5%" is another ([Help Net Security](https://www.helpnetsecurity.com/2024/09/16/open-source-software-dependencies/)). None of them reports how many suppressed findings later turned out to be reachable. Second, **nearly every vendor's third verdict means "we had no data or did not run", not "the code we analysed contains something we cannot resolve".** Socket goes further and folds analysis uncertainty into "reachable", so the user cannot tell real paths from conservative fallbacks ([Socket docs](https://docs.socket.dev/docs/static-reachability-analysis)). GitHub's "Potentially reachable" is the only documented analysis-uncertainty verdict, and it is not available for Python. No vendor documentation names `getattr`, `eval`, monkeypatching or config-string imports as constructs it handles or degrades on. On cost and access: none of the surveyed vendors documents free, no-account, call-graph-based function-level reachability for Python. One caveat: Endor's free AURI tier needs no account, and whether it includes reachability was not settled by the sources.

## Ten hobby repos already ship the feature list, so novelty is gone

The feature checklist a new tool might lead with was cloned many times in 2026. Every Python function-level reachability project found has 0 to 12 stars and is weeks to months old. reachvex claims function-level analysis, symbols mined from fix commits, a "first-class" `UNKNOWN`, OpenVEX output and fully offline operation. It reports that on its own example apps "only 13 of 93 raw alerts (14%) have a proven call path" ([reachvex](https://github.com/Krishita17/reachvex)). pyvulncheck rests on the idea that "the function the maintainer patched *is* the vulnerable function" ([pyvulncheck](https://github.com/ashflamer/pyvulncheck)). ca9, the only one with a steady release cadence, is import-level by default and "treats a false `UNREACHABLE` as the dangerous mistake" ([ca9](https://pypi.org/project/ca9/)). reachable-cve advertises cutting noise "by ~80%", yet its own PyGoat run marks 100 of 167 advisories reachable ([reachable-cve](https://pypi.org/project/reachable-cve/)). At least three near-identical repos named `reachable` promise "never a silent 'safe'" ([GitHub search](https://github.com/search?q=vulnerable+function+reachability+python&type=repositories)), which looks like a shared assignment. ProveItReachable self-reports precision 0.91 and recall 0.67 on 30 cases ([ProveItReachable](https://github.com/jegadeesh17/ProveItReachable)). The consequence is blunt: call paths, a three-state verdict, conservative unknowns, VEX/SARIF and offline mode are now table stakes in the hobby tier. **None of these projects has users, a reviewed symbol dataset or an evaluation on real third-party applications**, and that is where differentiation is still possible.

LLM-agent triage is the other 2026 entrant, and the evidence for it is mixed. On VEX-Bench (EMNLP 2026, 75 expert-labelled cases), GPT-5.5 and Claude Opus 4.6 reach about **80% F1** on binary affected/not-affected. Python is the weakest language, at 71.3% status F1 against 81.3% for Go, and cost ranges from $0.075 to $1.08 per case ([VEX-Bench](https://arxiv.org/pdf/2609.08040)). ZeroPath's commercial agent admits it "can miss reflection, dynamic dispatch, and deserialization" ([ZeroPath](https://zeropath.com/blog/reachability-exploitability-triage)). Practitioners distrust it for compliance: "I'd be weary to trust AI with something like that, especially if I had to assert to a third party" ([HN 47094192](https://news.ycombinator.com/item?id=47094192)). reachability-triage's own real-model lane supports keeping the LLM out of the headline. The project's write-up of its Phase 9 runs records most adversarial runs ending in `budget_exceeded` and states that real-model injection resistance is unclaimed ([DECISIONS.md §17](../DECISIONS.md)). An LLM can still rank candidate symbols inside a deterministic set, which is the role §26 already gives it. It should not decide verdicts.

## Two of 14,236 PyPI advisories name a function, so data is the real gap

The schema slot exists, but almost nothing fills it. The PyPA format supports `ecosystem_specific.imports` (module plus attribute) ([pypa/advisory-database](https://github.com/pypa/advisory-database)). A measurement of the full OSV PyPI dump on 2026-11-16 found **2 of 7,987 PYSEC records** using it, both for one package, `local-operator`. It found **zero** records with `affected_functions` ([OSV PyPI all.zip](https://osv-vulnerabilities.storage.googleapis.com/PyPI/all.zip)). The GitHub REST API returned **0 of 6,873 reviewed pip advisories** with non-empty `vulnerable_functions`, and the same was true for npm, Maven and Go ([GitHub REST](https://docs.github.com/en/rest/security-advisories/global-advisories)). reachability-triage's own count independently agrees: 2 of 14,236 live non-malware records ([APP_SCAN_RESEARCH.md:40](../agent_docs/research/APP_SCAN_RESEARCH.md)). GitHub's 79 curated Python advisories from 2022 are not visible in any public export. The OSV proposal for a unified affected-functions field has been open since March 2023 ([osv-schema#127](https://github.com/ossf/osv-schema/issues/127)). The Go comparison needs care. **956 of 1,241 reviewed Go reports (77%) carry symbols, but only 21% of all GO- records do**, because most new entries are now unreviewed imports ([OSV Go all.zip](https://osv-vulnerabilities.storage.googleapis.com/Go/all.zip)). This scarcity is why VEX-Bench limited its reachability baseline to Go: "reliable function-level records are available only for Go" ([VEX-Bench](https://arxiv.org/abs/2609.08040)).

Deriving symbols is therefore mandatory, and the published error rates are high. 56 to 64% of PyPI advisories carry a commit or FIX reference, which is an upper bound for patch mining ([OSV PyPI all.zip](https://osv-vulnerabilities.storage.googleapis.com/PyPI/all.zip)). Treating every changed function as vulnerable is a known trap ([Dunlap et al., DIMVA 2024](https://www.enck.org/pubs/dunlap-dimva24.pdf)). PyVul measured raw fix-commit labels at **40.4%** accuracy, rising to 94.2% only after LLM-assisted cleansing ([PyVul](https://arxiv.org/html/2509.04260v1)). "Hidden Amplifiers" got function names for 69% of 45 advisories at 84% precision ([arXiv 2607.05894](https://arxiv.org/pdf/2607.05894)). reachability-triage's approach intersects two weak signals, and that is defensible. "High" confidence means the symbol is named in the advisory text in code form *and* changed between the installed wheel and the first fixed wheel ([DECISIONS.md §26](../DECISIONS.md)). It also sets a coverage ceiling. In the project's 60-advisory hand sample, 30 of the 57 non-malware groups (**53%**) name a Python function anywhere in their text. Named symbols are often wrong for the purpose (mako names stdlib `cgi.escape`; TensorFlow names an op whose bug is in C++). A regex extractor scored precision 0.78 and recall 0.70. Only 35 of 57 (61%) have wheels on both sides of the fix ([APP_SCAN_RESEARCH.md:506-524](../agent_docs/research/APP_SCAN_RESEARCH.md)). So expect high-confidence targets for well under half of advisories. The rest land in `no_target_symbol`. Those labels also have a single rater ([APP_SCAN_RESEARCH.md:1123](../agent_docs/research/APP_SCAN_RESEARCH.md)), which has to change before anyone cites them.

The data shortfall is the strategic opening. A CC-BY-4.0 dataset mapping PyPI advisories to symbols would be a contribution on its own, with a confidence grade, the advisory text span and the diff hunk recorded as provenance for each entry. It would be more defensible than the scanner, and the upstream slot already exists. Contributing high-confidence entries to `pypa/advisory-database`'s `imports` field is the move that would make the project matter beyond its own users. Whoever fills that field defines Python reachability, as vuln.go.dev did for Go. Astral and Google would need the same data.

## No function-level Python benchmark exists, and 50 to 100 labelled pairs would lead the field

The benchmark slot is empty. The nearest neighbour is **VEX-Bench**: 75 cases, of which **20 are Python** across 10 projects. Its labels are project-level affected/not-affected with a justification category, not vulnerable function plus call path. Its labels split 29.3% affected and 50.7% not affected because the code is not reachable ([VEX-Bench](https://arxiv.org/pdf/2609.08040)). PyVul (1,157 vulnerabilities, 2,082 functions) and CVEfixes label vulnerable code, not reachability, and PyVul's repository carries no license ([PyVul repo](https://github.com/billquan/PyVul)). Jarvis's case study found 6 of 36 vulnerabilities reachable through 6 hand-confirmed chains. That is an illustration, not a released dataset ([Jarvis](https://arxiv.org/html/2305.05949v5)). For scale, hand-labelled reachability sets in the literature run from 20 to 30 cases per language (VEX-Bench) to 60 projects (Zapata et al., via [Alfadel et al.](https://diegoeliascosta.github.io/papers/Alfadel_EMSE2023.pdf)). **A Python set of 50 to 100 advisory-by-application pairs would sit at or above that norm.** Each pair needs the vulnerable symbol, a call path for the reachable labels, a reason for the not-reachable labels and an explicit dynamic/unknown class. Published Python-specific reachable shares are thin and scattered: 17% in Jarvis's n=36 study, 3 to 8% for native-library CVEs ([arXiv 2603.18693v2](https://arxiv.org/html/2603.18693v2)), and 29% mixed-language in VEX-Bench. A measured pure-Python rate on a public set would be a first.

The call-graph literature explains both why `not_reachable` is unsafe and why the tool's design choice is sound. PyCG reports about 99% precision and 70% recall on its macro-benchmark ([PyCG](https://arxiv.org/pdf/2103.00587)). Once dependencies are included in a whole-program graph, the numbers collapse: **PyCG 0.19 precision / about 0.5 recall, Jarvis 0.35 / 0.60** ([Jarvis](https://arxiv.org/html/2305.05949v5)). LLMs alone do worse than static tools. The best of 24 models got 60.3% of PyCG micro-benchmark cases complete, against PyCG's 84.9% ([Venkatesh et al., EMSE 2025](https://arxiv.org/html/2410.00603v2)). Hybrids help: InferCG's static candidates with LLM filtering add up to 13.9% recall over PyCG ([InferCG](https://dl.acm.org/doi/10.1145/3799990)). PyCG itself was revived on 2026-11-15 for Python 3.12+, with no evaluation yet ([vitsalis/PyCG](https://github.com/vitsalis/PyCG)). reachability-triage's two measured failures match the literature. On the Flask tutorial, `request.form` is a `cached_property` read, not a call, so a call graph answered `not_reachable` for werkzeug's multipart parser. On the FastAPI template, SQLAlchemy loads psycopg from a URL string through `__import__` ([APP_SCAN_RESEARCH.md:43-64](../agent_docs/research/APP_SCAN_RESEARCH.md)). Even govulncheck, with curated symbols, scored F1 25 on VEX-Bench's Go slice, and adding reachability to OSV-Scanner cut its recall from 100% to 85.7% ([VEX-Bench](https://arxiv.org/pdf/2609.08040)). Refusing to say `not_reachable` is the evidence-based position, not a timid one.

That choice changes what an honest evaluation looks like. A scanner that never issues `not_reachable` has **zero false `not_reachable` by construction**, so advertising that number would be misleading. The metrics that mean something are these: the precision of `path_proven` (are the paths real?); its recall against labelled-reachable pairs; and whether the evidence levels sort the truly not-affected cases toward `package_installed_not_imported` and the truly affected ones toward `module_imported_by_app`. The last of these is the only evidence that the graded `unknown` is worth more than a single `unknown` bucket.

## Citability takes a DOI, a datasheet and a second rater

The recipe is standard and cheap. Add a `CITATION.cff`, which GitHub turns into a "Cite this repository" prompt ([GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-citation-files)). Archive each release on Zenodo, which issues a concept DOI for the project and a version DOI per release. Reserve the DOI first, or the release's own CFF cannot contain it ([Turing Way](https://book.the-turing-way.org/communication/citable/citable-cff/); [arXiv 2609.28622](https://arxiv.org/pdf/2609.28622)). Release the data under CC-BY-4.0, which matches both upstream advisory databases, and add a datasheet covering collection method and known label noise ([Gebru et al.](https://arxiv.org/abs/1803.09010v2)). The 2026 ground-truth evaluation paper shows the pattern in this field: an arXiv preprint plus two Zenodo DOIs ([arXiv 2604.21111](https://arxiv.org/pdf/2604.21111)). The peer-reviewed home is the **MSR 2027 Data and Tool Showcase**. It explicitly excludes "datasets based on poorly documented or untrustworthy collection methods" and "artifacts resulting from the trivial application of existing tools" ([MSR 2027](https://2027.msrconf.org/track/msr-2027-data-and-tool-showcase-track)). A single-rater label set with no agreement statistic is exactly what that clause targets, so a second rater and an inter-rater score are the gating work. A short arXiv preprint is worth posting. Early arXiv release correlates with roughly 20% more citations, though confounders are unresolved ([arXiv 2404.16171](https://arxiv.org/abs/2404.16171v1); [arXiv 1805.05238](https://arxiv.org/pdf/1805.05238)). Any paper must position against VEX-Bench by its differences: Python only, function-level labels, call-path evidence and an explicit dynamic class. In this niche, citations go to the baseline others must beat (PyCG) or the benchmark others must run (VEX-Bench), not to tool descriptions.

## What reachability-triage can honestly say, and what it cannot

The app-scan design fixes the pitch. It outputs `reachable` with a proven path, or `unknown` at one of three evidence levels, each with a named reason such as "Frameworks often call such code for you (for example when you read `request.form`), which we cannot see" ([PHASE_APP_SCAN.md:255-268](../agent_docs/PHASE_APP_SCAN.md)). So it **does not reduce the number of advisories a team must consider. It orders them, and it proves the top of the list.** Given published reachable shares of roughly 3 to 30%, and reachvex's 14% proven-path yield, expect a minority of findings with a proven path. The rest are graded `unknown`, and a human still decides them. The tool also cannot produce the artifact compliance pressure is asking for. The CRA's reporting duties began on 2026-09-11 ([Travers Smith](https://www.traverssmith.com/knowledge/knowledge-container/the-eu-cyber-resilience-acts-vulnerability-and-incident-reporting-requirements-are-now-live/)), and practitioners want to "assert to a third party" that they are not affected. This tool emits evidence for "affected" and "under investigation", never a "not affected" justification. Pretending otherwise would put it in the noise-reduction market, where vendors' unverified 80 to 98% claims already set the tone and an honest tool loses.

What it can own is narrower and real. First, **every `reachable` is a checkable path, never a conservative fallback**. Socket's "reachable", by its own documentation, mixes the two. Second, **every `unknown` names the specific construct or data gap behind it**: opaque call, name escape, framework property read, config-string import, no fixed wheel. Commercial third states mostly mean "no data". Third, it runs **offline against a pinned, hash-checked OSV snapshot**, and that part is built today: the snapshot loader and matcher are in `src/reachability/scan/advisories.py` ([DECISIONS.md §27, item 10](../DECISIONS.md)). Fourth, it **publishes its symbol data and its evaluation**. The first two are design commitments until units A2 to A5 land. The fourth does not exist yet. The single-query engine behind `/v1/triage` does return path-or-reason verdicts today, with dynamic constructs degrading to `unknown` (`src/reachability/index/reachability.py:9-16`). The app scan does not yet call it.

## Conclusion

The gap is not "Python reachability": paid vendors have it, and hobby repositories have copied its surface. The real gap is the trust infrastructure underneath the category. That means an open, provenance-tagged PyPI symbol dataset, a public function-level benchmark, and a tool whose positive verdicts are proofs and whose uncertainty is itemised. That gap is moderate as a research and data contribution and small as a product. Its closing risk is concrete: Astral already lists reachability on `uv audit`'s roadmap, and anyone who ships it needs the same symbol data. The best outcome is not to out-feature uv or OSV-Scanner. It is to be the dataset and benchmark they adopt, which argues for upstreaming symbols into `pypa/advisory-database` and treating the scanner as the reference consumer of that data. Done in that order, the "never says unreachable" constraint becomes a credibility asset. Every number the project publishes will be a precision number with no suppressed findings hidden behind it.

**Recommended one-sentence pitch:** reachability-triage is a free, offline, open-source scanner for Python apps that shows the exact call path to every vulnerable dependency function it can prove your code calls, and gives a named reason for every advisory it cannot decide. It never marks one safe.

**Recommended headline README claim, once A2 to A5 ship:** "Every `reachable` finding includes a call path from your code to a function the security fix changed, which you can check line by line. Everything else is `unknown`, ranked by evidence and labelled with why. We never tell you a vulnerability is unreachable, because on the Flask tutorial a call graph would have been wrong about `request.form`."

**Claim that is true today, and should stand until then:** "Matches your lockfile offline against a pinned, hash-checked OSV PyPI snapshot. Function-level call-path evidence is in development."
